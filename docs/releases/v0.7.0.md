# Kitna v0.7.0 — proposed development release

Prepared on 28 November 2026. This is a development-signed build, not a published Play release.

## Changes

- Record a normal group expense using description, amount and Save. The full-screen editor defaults to you paying, equal shares, today's date and the selected group's active members. There is no mandatory review screen.
- Select several friends or a group from the main editor, or start from a friend's history. Create a local person inline without losing the expense draft. Non-group and personal expenses use hidden ledgers and do not create visible groups.
- Change payer, multiple contributions, split method, included participants and category in compact sheets. Equal, exact, percentage, shares and adjustment calculations use integer paise and reconcile exactly. Reselecting a method preserves its entered values.
- Keep date, receipt camera/picker and notes behind a bottom toolbar. Draft state survives subordinate sheets and saved-state recreation; meaningful changes get a discard warning. Stable expense IDs and save guards prevent duplicate writes, including retry after a committed non-group draft is restored.
- Use one Add friends screen for immediate local search, name-only friends, one selected contact, manual contact details and private invitations. Phone/email/account registration are optional for local records. No contact-book upload, public private-contact directory, phone authentication or SMS delivery was added.
- Create a local group with only a name, then add friends, share or skip. Add several existing friends to a group together. Joined, invited/local and departed participants keep their accounting identities.
- Share actual group/friend invitation URLs through Android's native share sheet. Copy links or seven-day group codes, or address an invitation to a verified Google email. Pending invitation routes survive OAuth, process recreation and app restarts.
- Review a private invitation and explicitly accept it. Protocol 3 never accepts email group invitations during synchronization; recipients choose Join from their inbox, link or code. Manual group codes retain protocol-2 acceptance compatibility before the server upgrade.
- Connect historical identities through verified email or explicit sender confirmation. Group-slot claims additionally require owner-authorized server verification. Forwarded unaddressed links cannot silently claim historical local balances; ambiguous shared slots are not automatically merged.
- Replace first-run tutorial steps with one concise start screen and an optional introduction. Keep the Manga Panels colors, artwork, typography, light/dark preferences and package identity.

Existing repayments, budgets, ownership transfers, notifications, receipts, history, backups, exports, Google PKCE/Keystore authentication, offline records, durable shared outbox and version-checked edits remain in place.

## Backend deployment

The protocol-3 migration is prepared and locally tested. **It has not been applied to production.** Apply it after the two existing `20261124` migrations only with deployment authorization. Neither previously deployed migration was modified; no reset is needed.

The migration adds private friend relationships/invitations, explicit group-email acceptance, safe previews, batch members, singleton groups, hidden ledger kinds and lookup indexes. RPCs enforce authentication, ownership/membership, verified claims, expiry, revocation and duplicate acceptance. Direct private-table writes remain denied. Run `supabase/verify_collaboration.sql` and the hosted security advisors after authorized deployment.

New friendship, preview, group-email inbox and batch-member workflows require protocol 3. Existing local tracking stays usable without a backend upgrade; manual group-code acceptance retains the older RPC fallback.

## Invitation hosting

Current development links use the supported `app.kitna` scheme. No controlled HTTPS invitation host has been supplied or verified. Verified App Links and automatic deferred deep linking are **not claimed**.

The build supports a configured `kitna.inviteHost`, restricted HTTPS routing, an autoVerify manifest filter, a safe static browser fallback, a signing template and an actual development-certificate assetlinks JSON. Deploy the fallback/association on a controlled host and test domain verification before calling HTTPS links operational. After installation, recipients can reopen the original link or enter the group code. See [APP_LINKS.md](../APP_LINKS.md).

## Install and data preservation

Install `releases/Kitna-0.7.0-dev.apk` over the existing app; do not uninstall to update. Package `app.kitna`, version code 7, Room schema 1, receipt paths and the established development signing identity are retained. Added serialized fields have compatible defaults, and per-version safety copies remain enabled.

Keep a complete exported ZIP when changing phones or reinstalling. Internal update copies do not survive uninstalling or clearing app data. No cloud schema or data was changed by building this APK.

## Remaining device and deployment checks

No physical phone or emulator is connected. Native renders and simulated UI tests do not establish real-device Google consent, two-account expense/receipt exchange, contact/camera provider behavior, TalkBack, actual IME/navigation-bar behavior, background notification delivery or HTTPS App Link verification. Those checks remain before a public release. Human task-completion timings were not measured.
